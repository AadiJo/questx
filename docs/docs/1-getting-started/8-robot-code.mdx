## Create and service QuestX

```java
import gg.questx.questx.QuestX;

private final QuestX questX = new QuestX();

@Override
public void robotPeriodic() {
  questX.commandPeriodic();
}
```

`commandPeriodic()` processes command responses and connection, tracking, and battery callbacks. Call it even when you consume measurements elsewhere.

## Robot-to-Quest mount

The robot-to-Quest transform is set on the headset, not in robot code. Open the web interface (`http://<Quest IP>:5801`), go to the **3D** tab, and choose the **Robot** view. Enter Forward (X), Left (Y), and Up (Z) in meters and Roll, Pitch, and Yaw in degrees, using WPILib robot axes (X forward, Y left, Z up). The transform runs from the robot origin to the headset's [Third-Eye Pose](./mounting#pose-origin) point. Edits preview live in 3D before you click **Save**. Each axis is limited to ±2 m and each angle to ±180°.

The headset publishes the robot's pose, computed as `headsetPose.transformBy(robotToQuest.inverse())`. This applies to `/QuestX/vioData`, `/QuestX/aprilTagData`, and the Limelight-compatible `botpose_wpiblue`. Only `headsetpose_wpiblue` still reports the headset center eye.

:::warning Do not apply the mount in robot code
Use `frame.fieldPose3d()` directly as the robot pose. Applying a `ROBOT_TO_QUEST` transform in robot code applies the mount twice.
:::

Saving a new mount starts a new VIO tracking epoch. The published pose jumps, so drop any VIO delta across it, the same as any other epoch change.

### Measuring robot-to-Quest {#measuring-robot_to_quest}

Measure the headset position from the robot estimator's origin along X (forward), Y (left), and Z (up). Include a rotation if the headset is not level and forward-facing. For a headset that is otherwise level and facing forward, upside-down is roll 180°, top rolled to the left (seen from behind) is roll −90°, and top rolled to the right is roll +90°. A rigid mount matters: motion between the headset and chassis appears as sensor motion.

The Camera tab's **Orientation** setting is display-only and does not change any pose. See [Mounting](./mounting#orientation).

### 3D tab

The web interface's **3D** tab has three views, drawn in the style of Limelight's field visualizer. The robot has bumpers in its alliance color with the configured team number on them. The alliance comes from the Driver Station (`/FMSInfo/IsRedAlliance`), or you can pick red or blue in the Field view.

- **Field** draws the full field from the loaded layout (carpet, guardrails, and alliance walls, plus simplified REBUILT or REEFSCAPE game elements placed on their own AprilTags) and the robot at a display-only field pose: VIO carried into the field by the most recent accepted AprilTag measurement. Robot code still does its own fusion. The view also shows the raw AprilTag solve as a robot with yellow bumpers that fades, lines from the camera to tags seen now, tag rims (green: used in the last solve; amber: seen now), a trail, and **VIO drift at last solve**, which is how far the VIO-aligned prediction was from each new tag solve.
- **Headset** shows each detected tag solved on its own in the camera frame, so ignored, unknown, and rejected tags appear too. Tags are drawn level with gravity around the headset, with ID, status, distance, and ambiguity.
- **Robot** is the mount editor described above. It warns when the Camera tab's Orientation and the mount's roll disagree, and offers a one-click fix.

## AprilTag measurements

Drain the queue so short-lived measurements are not lost. Apply team-specific rejection before updating the drive estimator.

```java
for (AprilTagFrame frame : questX.getAllUnreadAprilTagFrames()) {
  boolean qualityOk =
      frame.tagCount() >= 1
          && frame.inlierRatio() >= 0.50
          && frame.averageTagDistanceMeters() <= 6.0;

  if (!qualityOk) {
    continue;
  }

  // fieldPose3d() is already the robot pose; the headset applies the mount.
  drivePoseEstimator.addVisionMeasurement(
      frame.fieldPose3d().toPose2d(),
      frame.measurementTimestamp(),
      frame.pose2dStdDevs());
}
```

`measurementTimestamp()` is the queued NetworkTables server timestamp translated into the robot clock. Use it for latency compensation. The transmitted capture and app timestamps are diagnostic values.

The bundled standard deviations are a starting model, not a mandatory acceptance decision. Tune them from logs and consider tag count, inlier ratio, distance, robot motion, and innovation from the current estimate.

### Field-Bounds Filtering

Reject camera-derived robot poses outside the official field dimensions (plus a small tolerance) before calling `addVisionMeasurement()`. Also consider rejecting excessive innovation from the current drivetrain estimate; log the sequence ID and rule that rejected it.

## Local VIO measurements

VIO reports the robot origin in the Quest's local tracking frame. It is smooth and high-rate, but its origin is arbitrary. Consume it as a local-motion sensor:

```java
for (VioFrame frame : questX.getAllUnreadVioFrames()) {
  if (!frame.isTracking()) {
    continue;
  }

  if (frame.trackingEpoch() != activeTrackingEpoch) {
    activeTrackingEpoch = frame.trackingEpoch();
    resetLocalVioAlignment(frame);
    continue;
  }

  updateRobotOwnedFusion(frame);
}
```

Your robot-side fusion layer must maintain the rigid transform from the current VIO epoch to the field. Establish it from a trusted field observation and never calculate a VIO delta across an epoch boundary.

:::note
`setPose()` re-bases the published VIO frame: the next `VioFrame` reports the given position and yaw (roll and pitch stay measured) and carries a new `trackingEpoch`. The loop above therefore treats a reset like a recenter and drops the interval that spans it. The Quest rejects a reset while the headset is not tracking or while a recenter is settling.
:::

### Setting Robot Pose

Seed or reset the drivetrain pose estimator directly from the known autonomous starting pose, then initialize the current local-VIO-to-field alignment against that state or the first trusted AprilTag measurement. If robot code also calls `setPose()`, pass the robot pose; the headset converts it through the mount. The web interface's pose reset also takes a robot pose. VIO heading matches the field after the reset, but robot-side alignment must still restart at the new epoch.

## Freshness and connection

The last NetworkTables value persists after disconnect. Use `isConnected()`, `isTracking()`, sequence IDs, and measurement timestamps before accepting data.

```java
if (!questX.isConnected()) {
  // Fall back to drivetrain-only localization and alert the driver.
}

double vioAgeMillis = questX.getVioLatency();
double aprilTagAgeMillis = questX.getAprilTagLatency();
```

## Useful APIs

| API | Purpose |
|---|---|
| `getAllUnreadVioFrames()` | Drain local VIO measurements |
| `getAllUnreadAprilTagFrames()` | Drain field-relative tag measurements |
| `getLatestVioFrame()` | Inspect the newest VIO sample |
| `getLatestAprilTagFrame()` | Inspect the newest tag solve |
| `getVioLatency()` | Age of the newest VIO sample |
| `getAprilTagLatency()` | Age of the newest tag sample |
| `isConnected()` | VIO stream is fresh and NT is connected |
| `isTracking()` | Latest VIO sample reports valid tracking |
| `commandPeriodic()` | Service callbacks and command responses |

The old `PoseFrame` and `getAllUnreadPoseFrames()` APIs are retained temporarily for source compatibility with older Quest apps, but the new app does not publish a Quest-side fused pose.

## Debugging

Use the Quest web status page alongside robot logs. It shows:

- VIO and AprilTag publish counts;
- tracking state and epoch;
- tag IDs, corner inliers, distance, uncertainty, and measurement age;
- detector and passthrough camera failures;
- MJPEG client count and last-frame age.

Log every robot-side measurement decision with its sequence ID and rejection reason. That makes it possible to distinguish a Quest detector issue from a robot estimator policy issue.

### Publishing Diagnostics

Publish `isConnected()`, `isTracking()`, both latency values, active tracking epoch, latest sequence IDs, tag quality, and each rejection reason to your normal robot telemetry. Pair those values with the Quest web status page when debugging dropouts.
